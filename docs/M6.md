# M6 Sync

M6 syncs **encrypted host metadata** across devices. Password identities stay
`local_only` on each machine — you unlock with the same master password, then
re-enter host passwords (or use local keys) per device.

## Backends

| Backend | When to use |
|---|---|
| **HTTP** (`tethra-sync-server`) | ThinkPad / always-on Linux box over Tailscale |
| **File** | Dropbox, iCloud Drive, Syncthing, or a shared folder |

Conflicts resolve last-write-wins on item `version`, then `updated_at`, then keep local on an exact tie.

## ThinkPad over Tailscale

### Private repo on the ThinkPad

```bash
gh auth login          # GitHub.com → HTTPS → browser; allow private repos
gh auth setup-git
gh auth status

git clone https://github.com/AnthonyFiset/Tethra.git
cd Tethra
```

(Use `git@github.com:AnthonyFiset/Tethra.git` if you chose SSH.)

### Build and first-run wizard

```bash
# once, if needed
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"

cargo build -p tethra-sync-server --release
./target/release/tethra-sync-server
```

On first run (TTY), the binary:

1. Walks through data dir, listen address, token (generate or paste), client URL
2. Writes `~/.config/tethra-sync/config.toml` (mode `0600`)
3. Offers to install a **systemd user** unit (`tethra-sync.service`) — enabled for
   login/reboot, but not started immediately so the status TUI can bind the port
4. Opens a live status TUI (URL, token toggle, request counters)

Paste the printed **URL + token** into Tethra on Mac/Windows (**Vault sync → HTTP server**).

After installing the service, enable linger so it survives logout, then start it when you leave the TUI:

```bash
loginctl enable-linger $USER
# after quitting the TUI (q):
systemctl --user start tethra-sync
systemctl --user status tethra-sync
```

Or use `tethra-sync-server install-service`, which enables **and** starts the unit (use when you are not running the interactive TUI).

### Commands

| Command | Purpose |
|---|---|
| `tethra-sync-server` | Wizard if no config; else status TUI |
| `tethra-sync-server setup` | Re-run wizard |
| `tethra-sync-server serve` | Headless HTTP (what systemd runs) |
| `tethra-sync-server install-service` | Write/enable user unit |
| `tethra-sync-server uninstall-service` | Disable/remove unit |

Flags / env still override config: `--data-dir` / `TETHRA_SYNC_DATA`, `--listen` / `TETHRA_SYNC_LISTEN`, `--token` / `TETHRA_SYNC_TOKEN`.

Config lives at `$XDG_CONFIG_HOME/tethra-sync/config.toml` (default `~/.config/tethra-sync/config.toml`). The token is a shared bearer for Tailscale ACLs — not the vault key. Prefer Tailscale + token; do not expose port 8787 on the public internet.

### Updates

```bash
cd ~/Tethra
git pull
cargo build -p tethra-sync-server --release
# if the service points at this binary:
systemctl --user restart tethra-sync
# or re-run install-service after moving the binary
```

## Clients

### First device (creates the vault)

1. Create the vault and set your master password.
2. Open **Vault sync** (⋯ menu or ⌘K → “Vault sync”).
3. Choose **HTTP server**, set the Client URL from the wizard, paste the token.
4. Click **Sync now**. This publishes the vault header the other devices will adopt.

### Every other device (joins the vault)

> Do **not** create a vault on a second device. The vault key is random per
> vault, so a separately created vault cannot decrypt synced rows even with an
> identical master password.

1. On the welcome screen, click **Join a synced vault**.
2. Enter the Client URL (including `http://` and the port) and the token.
3. Click **Join synced vault**. The device adopts the shared header.
4. Unlock with the **same master password** as the first device.
5. Open **Vault sync** → **Sync now**.

Host rows appear; password fields stay empty until you save credentials locally.
After host edits, **Sync now** on the machine that changed, then on the others.

### Resetting a device that created its own vault

If a device already created a separate vault, sync refuses to run and reports
that the vault was created separately — this protects the shared header. Quit
Tethra and delete the vault database, then relaunch and use **Join a synced
vault**:

| OS | Path |
|---|---|
| Windows | `%APPDATA%\tethra\vault.sqlite3` |
| macOS | `~/Library/Application Support/tethra/vault.sqlite3` |
| Linux | `~/.local/share/tethra/vault.sqlite3` |

Deleting this file destroys any locally saved passwords on that device; hosts
come back from the server. If the device already has sync settings saved, it
adopts the shared header automatically at the next launch.

## Shared folder

Same dialog → **Shared folder** → pick a directory every client can write
(Dropbox / Syncthing / etc.). Layout on disk:

```
manifest.json
vault-header.json
items/<uuid>.json
```

## Secret boundary

- Only opaque ciphertext blobs leave the device.
- Sync never moves password identity rows.
- The HTTP token is a shared bearer (base64 in `Authorization`); it is not a vault key.

## Desktop installer releases

Push a version tag to build installers via GitHub Actions:

```bash
git tag v0.1.0
git push origin v0.1.0
```

The **Release** workflow produces:

- macOS `.dmg` (Apple Silicon + Intel)
- Windows `.exe` (NSIS)
- Linux `.deb` / AppImage
- `tethra-sync-server` Linux binary artifact (Actions Artifacts, not always on the Releases assets list)

Draft releases are created automatically; review assets before publishing.
You can also run the workflow manually from the Actions tab (`workflow_dispatch`).

Unsigned personal builds are expected until Apple/Windows signing certs are configured.
On macOS after install: `xattr -cr /Applications/Tethra.app`.
